# النظرة التقنية
## AuthKit

## 1. مكونات النظام (System Components)

يتكون النظام من ثلاثة مكونات رئيسية:

### Backend

الخدمة المركزية المسؤولة عن تنفيذ منطق المصادقة وإدارة الهوية والجلسات، وتوفير الوظائف للتطبيقات الأخرى من خلال REST API.

### Authentication SDK

مكتبة برمجية تسهّل على المطورين دمج خدمات النظام في تطبيقاتهم، وتوفر طبقة تعامل واضحة مع REST API بدلاً من تكرار تفاصيل الاتصال ومعالجة الاستجابات في كل تطبيق.

### Flutter Demo App

تطبيق تجريبي يوضح طريقة استخدام Authentication SDK والتحقق من تكامله مع Backend. لا يُعد هذا التطبيق المنتج النهائي للمشروع.

## 3. نظرة عامة على REST API (API Overview)

يتضمن الإصدار الأول خمسة مسارات أساسية:

| Method | Endpoint | الوظيفة |
|---|---|---|
| POST | `/auth/signup` | إنشاء حساب مستخدم |
| POST | `/auth/signin` | تسجيل الدخول |
| POST | `/auth/signout` | تسجيل الخروج |
| GET | `/auth/me` | جلب بيانات المستخدم الحالي |
| GET | `/auth/validate` | التحقق من صلاحية الجلسة |

تفاصيل Headers وRequest Body وResponse وHTTP Status Codes ومعالجة الأخطاء ستوثق بصورة مستقلة في تصميم REST API باستخدام Postman.

## 4. الكيانات الأساسية (Core Entities)

### User

يمثل حساب المستخدم العادي، ويحتوي على بيانات التعريف وبيانات المصادقة والبيانات الإضافية التي سيحددها تصميم قاعدة البيانات.

### صلاحية المدير (Admin Role)

يمثل المدير دوراً أو صلاحية يملكها حساب **User**، ولا يمثل كيانا مستقلاً في نموذج البيانات. تُخزن حالة الصلاحية الإدارية ضمن بيانات المستخدم، ولا يتضمن الإصدار الأول واجهة إدارية أو مسارات عامة لإدارة حسابات المديرين؛ وتتم إدارة هذه الصلاحية خارج واجهات الاستخدام العامة.

### Session

يمثل جلسة استخدام مرتبطة بالحساب، وتُستخدم لدعم التحقق من هوية المستخدم وصلاحية الجلسة وإنهائها عند تسجيل الخروج.

> الحقول والعلاقات والقيود النهائية لهذه الكيانات ستحدد في ERD ووثيقة تصميم قاعدة البيانات.

## 5. الافتراضات (Assumptions)

- النظام مكوّن مستقل ستستخدمه تطبيقات أخرى، وليس تطبيقاً نهائياً بحد ذاته.
- تطبيق Flutter مخصص لعرض التكامل واختباره.
- منح صلاحية Admin وإدارتها يتم خارج واجهات الاستخدام العامة في الإصدار الأول.
- تفاصيل آلية الجلسات وطريقة تمثيل بياناتها ستعتمد بعد دراسة متطلبات الأمان والتصميم.

## 6. القيود (Constraints)

- يركز الإصدار الأول على وظائف المصادقة الأساسية المحددة في نطاق المشروع.
- لا يتضمن الإصدار الأول تكاملاً مع مزودي تسجيل دخول خارجيين.
- لا يتضمن الإصدار الأول لوحة تحكم إدارية أو نظام صلاحيات متقدماً.
- يجب أن يبقى SDK قابلاً لإعادة الاستخدام وألا يعتمد على تفاصيل تطبيق Flutter التجريبي.

## 7. الاعتماديات بين مراحل المشروع (Project Dependencies)

يُنفذ العمل وفق ترتيب يقلل إعادة العمل ويحافظ على وضوح المخرجات:

1. تحليل المشروع وتحديد نطاقه ومتطلباته.
2. تصميم ERD وتوثيق قاعدة البيانات.
3. تصميم REST API وتوثيقها واختبارها باستخدام Postman.
4. وضع التصميم المعماري وتحديد مسؤوليات المكونات.
5. تنفيذ Backend واختبار مسارات API.
6. تطوير Authentication SDK وربطه بالـ Backend.
7. تطوير Flutter Demo App ودمج SDK.
8. تنفيذ اختبارات التكامل وإكمال التوثيق.

يعتمد تصميم REST API على الكيانات والعلاقات التي يتم اعتمادها في ERD، كما يعتمد تطوير SDK على عقد API مستقر وواضح.
